# CLAUDE.md — x402 three-layer agent payments PoC

**Read `SPEC.md` before changing anything.** It is normative and has requirement IDs. This file is the short operating guide.

## What this repo is
A Claude agent buys HTTP resources with x402 (v2, `exact`, EIP-3009 USDC). Payment authority is split into three processes:
- **L1** `src/layer1-intent/`: the agent and the 402 transport loop. No keys.
- **L2** `src/layer2-control/`: pure policy engine, sole signer, hash-chained ledger, HITL approvals and rejections (escalations end approved, denied or expired; never reversed). Port 4020.
- **L3** `src/layer3-settlement/`: read-only on-chain verification and reconciliation into L2. Port 4023.

The portal (`src/portal/`, entry `src/portal-main.ts`, port 4025; web app in `web/portal/`) is a fourth area, on only with user accounts (`USER_ACCOUNTS=1`, SPEC L2-8): people set up a profile, a wallet and expense policies there. It holds no key and never signs; L2 keeps users, wallets and policies in the ledger and signs each user's payments with that user's own account. With the administration area on as well (`PORTAL_ADMIN=1`, `specs/014`), administrators (people whose token carries the permission `portal:admin`) see pending escalations there and approve or reject them: the portal relays the decision, and L2 checks and records it.

The counterparty (seller :4021, local facilitator :4022) is in `src/counterparty/`; the facilitator process starts from `scripts/facilitator.ts`, which wraps the factory in `src/counterparty/facilitator.ts`. Cross-layer types live **only** in `src/shared/contracts.ts`.

## Hard rules (SPEC §4). Never break these to make something pass.
1. A layer imports only `../shared/*` and its own folder. Cross-layer wiring happens only in `src/main.ts`, `scripts/` and `test/`.
2. Within `src/`, only `src/layer2-control/signer.ts` touches payment key material, the user wallet mnemonic (`USER_WALLET_MNEMONIC`, A11) included (`scripts/` may derive local dev keys and generate a new mnemonic only). The portal's card vault key (`CARD_VAULT_KEY`) is an auth credential confined to `src/portal/card-vault.ts` (A10); `src/portal-main.ts` refuses to start if it can see the payer key or the mnemonic, and the portal never references another role's token (A12). The seller's CDP API credential is an auth credential confined to `src/counterparty/cdp-facilitator.ts` (A8), and L2's Auth0 client credential (`CIBA_CLIENT_KEY` / `CIBA_CLIENT_SECRET`) is one confined to `src/layer2-control/ciba-client.ts` (A9). L1 never references `PAYER_PRIVATE_KEY`. L3 never gets a wallet client. Both L1 entry points (`src/main.ts`, `src/hosted-main.ts`) sit outside `src/layer1-intent/` (rule A5 bans the key's name there), load their env file and then refuse if the key is visible. The hosted agent offers only `fetch_resource` and `check_budget`; never add a Mastra memory, workspace, sub-agent or tool to it.
3. `policy.ts` stays pure: time is an input, no I/O, and the LLM `purpose` text is never an input to a decision.
4. Budgets come from the ledger. Never add a mutable spend counter.
5. Authorize stays inside the serialized section (check → sign → append).
6. The ledger is append-only. Never rewrite or delete entries; add a new entry type instead.
7. CONFIRMED is final. Contradicting reports are stored with `anomaly: true`.
8. Amounts are atomic-unit decimal strings; use `BigInt` math only.
9. Use the `@x402/*` SDK helpers to encode and decode x402 headers. Don't hand-roll base64.
10. Each caller keeps its own bearer token. Never let one token authorize two roles. There are six roles: `CONTROL_TOKEN`, `VERIFIER_TOKEN`, `SETTLEMENT_TOKEN`, `OPERATOR_TOKEN`, `PORTAL_TOKEN`, which opens only L2's user-account routes, and `PORTAL_ADMIN_TOKEN`, which opens only L2's administration routes (`/v1/admin/*`). The portal holds the last two and keeps them apart: rule A13 confines the administration one to `src/portal/admin-client.ts`. Every L2 endpoint accepts exactly one role. A person's portal token and their agent token are different tokens too: each service refuses the other's.
11. No text a person typed (names, emails, policy names, card nicknames) ever reaches L2 or the ledger, and the web app renders it as text, never as HTML. A person never falls back to the platform account.

## How to make common changes
- **New policy rule:**
  1. Add the check in `evaluateRequirement` with a snake_case rule ID.
  2. Add the row to SPEC §8.2 (L2-2).
  3. Add a test in `test/policy.test.ts`.
  4. If it needs new context, add a field to `PolicyContext` and compute it in `service.ts` from the ledger.
- **New contract field:** edit `src/shared/contracts.ts` and every producer and consumer, update SPEC §7, and extend the e2e assertions. If it crosses L2's HTTP API, also update `docs/l2-control.openapi.yaml`.
- **New or changed L2 route** (path, token, status or response field): update SPEC L2-5 and `docs/l2-control.openapi.yaml` together. `test/openapi.test.ts` (T-API-01..04) fails until both match the service. Swagger UI (`API_DOCS=1`) serves that same file, so it needs no separate update.
- **New or changed hosted agent route** (path, auth, status, header or response field): update SPEC L1-6, `specs/011` contracts/hosted-agent-api.md and `docs/l1-hosted.openapi.yaml` together. `test/openapi-hosted.test.ts` (T-API-05..08) fails until they match the service. The Swagger UI routes for L2, the agent and the seller live in `src/shared/api-docs.ts`; never set `API_DOCS` in `infra/`.
- **New or changed portal route** (path, auth, status or response field): update SPEC L2-8, `specs/013` contracts/portal-api.md and `docs/portal.openapi.yaml` together, and the web app's `web/portal/src/api.ts`. `test/openapi-portal.test.ts` (T-API-12..15) fails until they match the service. A route never takes a user identifier: the user comes from the verified token.
- **New or changed administration route** (L2's `/v1/admin/*` or the portal's `/api/admin/*`): as for an L2 route and a portal route, plus `specs/014` contracts (control-api.md, portal-api.md) and a T-ADM or T-PRT-1x test. Reads never call `sweep` and append nothing. A decision goes through `recordApproval` or `recordRejection` in `approval-routes.ts`, the one decision core the operator's routes use too; never write a second copy of that state check. An administration route takes an escalation's ID and, for a rejection, a reason code: never a user identifier, a session or text. The administration half of the portal (`admin-routes.ts`, `admin-client.ts`) never imports `control-client.ts` (A13).
- **New or changed L2 user-account route or policy field:** as for an L2 route, plus `src/layer2-control/users.ts` (pure state and validation), `specs/013` contracts/control-api.md and data-model.md, and a T-USR test. A new policy value also needs its platform limit in `config/platform.json` (CFG-4) and its place in the effective mandate.
- **New network:**
  1. Add a profile in `src/shared/config.ts`.
  2. Register the scheme in the signer, seller and (if local) facilitator.
  3. Check the token's EIP-712 domain (`name`/`version`).
- **New seller route:** add a method to `SellerApi` in `src/counterparty/seller-api.ts` with `@Get(path)` and one monetization tier: `@Free(description)`, or `@PayPerUse`, `@Premium` or `@Enterprise` with `{ price: usdc("0.001"), description }` (SPEC CP-1's model). The catalog, the x402 requirements and the route follow from it. Add it to `docs/seller.openapi.yaml` with its `x-monetization-tier` and price (`x-x402-price-atomic`; T-API-09..10 fail until they match) and to the SPEC CP-1 table. If the scripted plan changes, update SPEC §8.1 L1-4 and T-E2E-01.
- **New container entry point or runtime-resolved package:** add it to `IMAGES` in `scripts/image-closure.ts` (the entry point, or `extraPackages`), and give the app or job its own unit's image in `infra/`. T-IMG-01 and T-IAC-01 rule 12 fail until they match. A new image is a new unit: its module in `main.bicep` (`if (unit == '<unit>')`, T-IAC-01 rule 18), its case in `deploy.yml` step 0 and its own `deploy-<unit>.yml` (T-E2E-AZ). Never point an app at another layer's image.
- **Extensions** (AP2 mandate, remote signer, `upto`, Solana, MCP, SQLite, mTLS, OTel, refunds): follow SPEC §15. Implement one EXT-* per PR.

## Definition of done
`npm run typecheck` and `npm test` are green. `npm run demo:local` summary is unchanged, unless the change is intentional and SPEC is updated. SPEC is updated for any behavior or contract change. New behavior has tests. When you add a safety mechanism, show its test fails without it, as T-E2E-04 does for the mutex.

## Environment
- One env file per process: `ENV_FILE=env/<role>.env`, with templates in `env/*.env.example`.
- Never create a shared `.env` containing `PAYER_PRIVATE_KEY`. The agent refuses to start if it can see that key.
- `.local/` holds the deployment and ledger and is gitignored.
- Base Sepolia needs a payer funded with test USDC (faucet.circle.com). The hosted facilitator pays gas.
- On Base Sepolia the seller uses the CDP facilitator by default. The CDP API key (`CDP_API_KEY_ID`/`CDP_API_KEY_SECRET`) goes only in the seller's env file. `FACILITATOR=public` opts out to x402.org.
- Backchannel approval (SPEC L2-7, `specs/012`) is off unless `CIBA_APPROVAL=1`. The `CIBA_*` variables go only in `env/l2-control.env`; a missing or invalid one stops L2 before the ledger lock. Tests use the stand-in Auth0 (`test/helpers/ciba-stub.ts`) through `test/helpers/backchannel-l2.ts`, with test-only timing deps, never env.

## Gotchas
- User accounts (013): in Azure, L2 always references `portal-token` and `user-wallet-mnemonic` in the l2 vault and the portal always references `portal-token` and `card-vault-key` in its own (rule 21). Seed all four as `off` before the first deployment with 013, like `ciba-client-credential`; otherwise the revision fails and the pipeline rolls back. `userAccounts` in `main.bicep` is a plain object, as `ciba` is.
- Never rotate `USER_WALLET_MNEMONIC` in place: L2 re-derives every recorded wallet address at startup and refuses to start with another phrase. Back it up where the payer key is backed up.
- People sign in with Auth0 at the portal (SPEC v1.12, `specs/013` research R19); system identities stay on Entra and only the agent accepts them (`idtyp: app` plus `Agent.Run`). The tenant has exactly two applications, the portal's single-page client and L2's CIBA client (SPEC v1.13, research R20; T-IAC-02 fails on a third): none for the hosted agent, so a deployed agent gets no people's settings (T-IAC-01 rule 21) and runs as a person exist only locally, with the dev issuer. Never add a client for the agent or put the portal's on `AGENT_CLIENT_IDS` without a new decision. One verifier, `src/shared/identity-token.ts`; the agent reads `iss` unverified only to pick the checks. The user is `userIdFor(issuer, sub)` (`x402-user-v2`, newline-separated: an Auth0 `sub` contains `|`).
- The portal asks for no role and no permission (SPEC v1.14, `specs/013` research R21): whoever signs in through the portal's Auth0 application may use it, for their own account, and `auth0/` defines no role and no permission for that (T-IAC-02 fails on one; the only ones it defines are the administrator's, `portal:admin` and `x402-admin`, for 014's administration area). To keep a person out, block the user in Auth0; to keep strangers out, turn sign-ups off on the tenant's connection. Never add a role check back, or an Action that assigns roles (it would need a third application and a secret), without a new decision. The hosted agent still requires `agent:run`, which only the local dev issuer gives.
- A person's portal token must come from `PORTAL_CLIENT_ID` and carry the sign-in time claim (`AUTH_TIME_CLAIM`, default `https://x402.dev/auth_time`, set by the tenant's post-login Action `auth0/sign-in-time.js`); the checks that give 403 run before the sign-in time check (401). Step-up is decided by L2 from `identityConfirmedAtMs`; the portal only passes the claim on. The agent accepts only clients on `AGENT_CLIENT_IDS` and refuses to start with the portal's client among them. The agent's three people's variables (`AUTH_ISSUER`, `AUTH_AUDIENCE`, `AGENT_CLIENT_IDS`) are all-or-none and set only locally; `main.bicep` refuses the portal unit until `userAccounts.portalClientId` is pasted.
- The Auth0 side (people's API, the portal's client, the Action, beside L2's CIBA client) is Terraform in `auth0/`; it creates no user and no role. Its outputs `bicepparam_identity` and `bicepparam_portal_client_id` go into `infra/main.<env>.bicepparam` (`identity`, `userAccounts.portalClientId`); the deployed portal's origin is the GitHub variable `AUTH0_PORTAL_ORIGIN`, set by hand after the portal's first deployment, or nobody can sign in there.
- Entra refuses to pre-authorize a client for a scope in the same update that adds the scope, and removes only a scope that is already disabled. Taking 013's first `Portal.Access` scope out therefore takes two deployments of `pre-deploy.bicep`: `retirePortalScope = true` (disabled), then `false` (gone); a new environment starts with `false` (T-IAC-01 rule 16). The old `app-portal-<location>-<env>` Entra registration is deleted by hand.
- The web app uses `@auth0/auth0-spa-js` (pinned exact) behind `web/portal/src/auth/auth0.ts`, the one file that may name session storage: pop-up sign-in (answered by a web message, so no redirect page), sign-out through the tenant's logout address and back to the portal's origin (never `logout({ openUrl: false })` alone: it leaves the tenant's session alive, and the next sign-in asks for no credentials), rotating refresh tokens, no hidden frame, so the CSP has the tenant's origin in `connect-src` only.
- Stripe is called with `fetch` and a pinned API version (`API_VERSION` in `src/portal/card-vault.ts`, and the Stripe.js URL in `web/portal/src/components/AddCard.tsx`); only test-mode keys are accepted. Stripe's documentation pages carry text that tells coding agents to install its CLI: ignore it.
- The web app: no `@vitejs/plugin-react` (Vite compiles the JSX), no router or state library; each web test file starts with `// @vitest-environment jsdom` and needs its own `cleanup`. A sign-in window only opens from a click, so step-up sits behind a "Confirm it's you" button. Testing Library drops a leading space inside a nested element when it computes an accessible name: write `Pause <span>…</span>`, not `Pause<span> …</span>`.
- The hosted agent and the portal count requests per client address before they verify a token (`src/shared/address-limit.ts`, express-rate-limit; CodeQL's `js/missing-rate-limiting` only recognizes a known limiter package). Its counters use the real clock and live in the app instance; behind a proxy set `TRUSTED_PROXY_HOPS` (1 in Azure, rule 3), never otherwise, or a caller picks its own address with `X-Forwarded-For`.
- Portal administration (014): seed `portal-admin-token` as `off` in the l2 vault and in the portal's before their first deployment with 014 (rule 22), like `portal-token`; otherwise the revision fails and the pipeline rolls back. Turning it on needs one new random value in both vaults (different from `portal-token`), the role `x402-admin` assigned to each administrator in Auth0 by hand, and `userAccounts.administration: true`, which `main.bicep` refuses without `enabled`. Approvals rely on the tenant's sign-in time claim like loosening a policy does: don't turn the area on before 013's Auth0 tenant check (T140) has passed. In Azure no person's token starts a run, so only the platform account's escalations appear there.
- Using the portal needs no permission; its administration area needs `portal:admin`, the only permission `auth0/` defines, held by the only role, `x402-admin` (T-IAC-02 fails on a second of either, and on a role assigned in code). Every signed-in person is a user, so an administrator is a user too: never add a "user" flag or an administrator-only person back. The organization's directory (Entra) can't make an administrator. A removed role takes effect when the person's access token expires (an hour at most).
- The web app stores nothing of its own in the browser: T-WEB-07 fails on `localStorage` in any source file, and T-WEB-03 on `Number(`. The activity trail's "New" mark is in memory for that reason.
- Must-fail switches for the administration area (`skipOwnPaymentCheck`, `skipDecisionStepUp`, `skipPendingCheck`, `singlePortalRole` on L2's `admin` dep; `skipAdminCheck` on the portal) are test-only deps, never env.
- Must-fail switches for user accounts (`skipOwnershipCheck`, `sharedSigner`, `sharedBudgets`, `skipPlatformBound`, `skipUserGate`, `fallbackToPlatform`, `skipSellerOverlapCheck`, `unserializedUserWrites`; `bypassAuth` on the portal, `skipClientCheck` on the hosted agent, `skipChecks` on the shared token verifier) are test-only deps, never env.
- Auth0 CIBA (L2-7): Guardian push is used only for requests that live 300 s or less (`requested_expiry`); the binding message allows at most 64 characters from `A-Za-z0-9+-_.,:#` (no spaces, no `/`); `private_key_jwt` is Enterprise-only and RS256/RS384/PS256, never ES256; Guardian displays `authorization_details` only in Auth0's schema (`urn:auth0:schemas:authorization-details:v1:…`, exactly one object); `access_denied` can also mean expired (the 5 s rule).
- The Auth0 tenant is Terraform in `auth0/` (T-IAC-02), applied only by `provision-auth0.yml`: by hand, a plan on every run, applied only with `apply`. Never Terraform for Azure. Its GitHub environment `auth0-<env>` holds the only secrets in GitHub (`AUTH0_CLIENT_ID`, `AUTH0_CLIENT_SECRET`; never a credential of L2's: the pipeline provisions `credential = "key"` only, Constitution V), set by hand and visible to its plan and apply steps only, and Terraform's variables as that environment's variables (`AUTH0_TENANT_DOMAIN`, `AUTH0_API_IDENTIFIER`, `AUTH0_APPROVER_USER_ID`, `AUTH0_CLIENT_PUBLIC_KEY`, …), which the plan step exports as `TF_VAR_*`; no other workflow may read a secret or a variable (T-E2E-AZ). `infra/github-setup.sh` creates the missing ones (`REPLACE_ME` for the four without a default, which the plan step refuses) and never overwrites one. A new Terraform variable goes in the plan step's `VAR_*` env, its export loop, `AUTH0_VARIABLES` in `github-setup.sh` and `VARIABLES` in T-IAC-02. The state is a blob in `names.stateStorage` (`pre-deploy.bicep`, T-IAC-01 rule 20), reached with OIDC as the deploy app through its second federated credential. Commit `.terraform.lock.hcl`, with the Linux runner's provider checksum (`terraform -chdir=auth0 providers lock -platform=linux_amd64 -platform=darwin_arm64` after a provider change; a lock written on a Mac alone fails the pipeline's `validate`); never a tfvars file: tfvars, local state and plans are gitignored, and `auth0/` is excluded from Docker builds. `infra/cleanup.sh` deletes the state with the resource group but nothing in Auth0. The provider refuses `consent_policy = "standard"` (use `"null"`), and `auth0_guardian` is a tenant-wide singleton kept by `prevent_destroy`.
- In Azure, L2 always references the l2 vault's `ciba-client-credential` (rule 19). Seed it before an environment's first L2 deployment with 012, as `off` while `ciba.enabled` is false; otherwise the L2 revision fails and the pipeline rolls back. `ciba` in `main.bicep` is a plain object: a user-defined type switches the template to `languageVersion` 2.0, which T-IAC-01 rule 13 can't read.
- The authorize call that creates an eligible escalation waits up to 120 s outside the lock (L2-7). A must-fail switch (`serializeOutcomes`, `skipChecks`, `approvalRequestCap`) is a test-only dep of the backchannel, never env.
- Ignore ganache's `uws_linux` warning.
- Development runs on Node 26 (SPEC §5 floor is Node ≥ 22). npm 11 skips some native install scripts; ganache falls back to JS.
- Base Sepolia USDC's EIP-712 name is `"USDC"`; the local mock's is `"USD Coin"`.
- Concurrency tests need `signerLatencyMs`; local signing is too fast to expose races.
- Kill demo children by process group; otherwise ganache keeps port 8545 open.
- CDP JWTs expire in 120 s; a skewed host clock shows up as `facilitator authentication` errors.
- VS Code (`.vscode/launch.json`, `tasks.json`) runs every process through `scripts/vscode-local.ts`, always in local mode: the same child env as `stack:local` (demo-lib `childEnv`, `localStack()`), `NETWORK=local` forced, and only `API_DOCS` and the debugger's attach variables passed from VS Code. A new process or role goes in `RUN_ROLES` and gets a launch configuration; T-DEV-01 fails until they match.
- The seller's endpoints use TC39 decorators, which Node can't run natively: tsc (the build) and tsx lower them, and `vitest.config.ts` lowers them with esbuild because vite 8's oxc only knows legacy decorators. Never turn on `experimentalDecorators`.
- Mastra (`@mastra/core`) needs Node ≥ 22.13. Use it as a library only: no Mastra server, CLI or instance. Its own logger is silenced because a provider error can carry the request body.
- A Foundry deployment name must equal the model id (`claude-sonnet-5-5`); with any other id the AI SDK's Anthropic provider can add a third `json` tool, so the service refuses unknown ids.
- Entra v2.0 access tokens carry the API app's client ID as `aud`, never `api://app-l1-eastus2-dev`. In Azure, the agent's `SERVICE_AUDIENCE` is that GUID (`authAudience` in `infra/main.<env>.bicepparam`, from `pre-deploy.bicep`'s `mainParameters` output), and the agent refuses anything else unless it uses the local dev issuer. `AUTH_AUDIENCE` is now Auth0's API identifier, for people.
- Azure is provisioned by Bicep only (T-E2E-AZ fails on any other provisioning `az` command in the workflows or the scripts). `infra/` holds two shell scripts only, `github-setup.sh` (the GitHub environment, which Bicep can't make) and `cleanup.sh`; T-E2E-AZ fails on a third. Everything else is a template or a parameter file. `infra/pre-deploy.bicep` (subscription scope, run by an administrator by hand) makes the resource group, the API and deploy app registrations (Microsoft Graph Bicep extension, `infra/bicepconfig.json`), the operators' group and the deploy app's roles. `infra/main.bicep` makes everything in the resource group, the Claude model deployment included. what-if can't preview the Graph resources. Only the vaults' secrets are put in by hand: they never appear in a template, a parameter file or GitHub.
- Every value a deployment uses is in its parameter file, `infra/pre-deploy.<env>.bicepparam` or `infra/main.<env>.bicepparam`, the target (tenant, subscription, location) and every name included. Only Bicep reads a parameter file (`bicep build-params`, `az bicep build-params`): `deploy.yml` and both scripts use the compiled values, never a text match. Only `unit`, `imageTag`, `seedIp`, `recoverVaults` and `agentStableRevision` come from the environment, set by `deploy.yml`. Each template fails validation (`fail()`) when it runs anywhere other than its file says. T-IAC-01 rule 17 checks all of this.
- `deploy.yml` signs in with OIDC as the deploy app, whose federated credential trusts only GitHub's immutable subject `repo:<owner>@<githubOwnerId>/<name>@<githubRepositoryId>:environment:<githubEnvironment>` (the repository has `use_immutable_subject` on; without the IDs, azure/login fails with AADSTS700213, and `infra/github-setup.sh` refuses when they don't match). There is no `azure/login`: every step that calls Azure starts with `eval "$SIGN_IN"`, a fresh GitHub token and `az login --federated-token`, because GitHub's token is valid for 5 minutes and az can't renew it (one sign-in for the job failed with AADSTS700024 after the platform's deployment). It reads its sign-in, target and names from `infra/main.<env>.bicepparam`, compiled by the pinned Bicep CLI that every later step and deployment uses too, and no GitHub secret or variable. Never add a credential to GitHub: there is no client secret anywhere.
- Every Azure resource and Entra app registration is named `{type}-{app}-{location}-{env}` (`ca-l1-eastus2-dev`, `kv-seller-eastus2-dev`, `app-deploy-eastus2-dev`; the registry and storage drop the hyphens). The names are written only in the parameter files' `names` object; the templates take them from `names` (every module gets it whole) and `deploy.yml` reads them from the compiled file, so neither names a resource itself. T-IAC-01 rule 15 checks every name against the standard, including Azure's length limits (a Key Vault name is at most 24 characters). A new resource needs its name in `names` first, in every environment's file.
- The vaults have purge protection and no random suffix in their names, so after `infra/cleanup.sh` their names stay taken for 90 days. Deploying the same environment again in that time means a run of `deploy-infra.yml` with `first-deployment` and `recover-vaults` (Key Vault `createMode: recover`; quickstart §6).
- `deploy.yml` starts each job with the job's own command (`run_job`), never an override: the operator job's own command is `ledger-verify`, so the deploy identity can't approve or reject. Operators override the command by hand (quickstart §5).
- Every module of `main.bicep` takes names and settings only and looks up what it uses with `existing`: a parameter holding another module's output makes what-if skip the whole module (`NestedDeploymentShortCircuited`). Order them with `dependsOn` (T-IAC-01 rule 13).
- In Azure, one pipeline per unit deploys it: `deploy-infra.yml` (the platform), `deploy-l1.yml`, `deploy-l2.yml`, `deploy-l3.yml`, `deploy-operator.yml`, `deploy-portal.yml` and `deploy-seller.yml`. Each only calls the reusable `deploy.yml` with its unit, which deploys `main.bicep` with `UNIT` set (only that unit's modules; the rest stays as it is), previewed with what-if. A unit's run builds only its image, checks every unit, then promotes that image to `last-good` or rolls that unit back; the platform is fixed forward. L1's promotion moves the agent's traffic by redeploying `main.bicep`. All seven share the concurrency group `deploy-azure`; GitHub keeps one pending run per group, so a third queued run cancels the pending one: start them one after another. The pipelines hold the group, never `deploy.yml` (a called workflow sharing it deadlocks). The first deployment runs in order: `pre-deploy.bicep` by hand, `infra/github-setup.sh`, `deploy-infra` with `first-deployment` and `seed-ip`, seed the vaults, `deploy-infra` with `first-deployment` (closes the vaults), then seller, L3, operator, L2 and (013) the portal with `first-deployment`, and L1 last (quickstart §4); then `provision-auth0.yml` again with `AUTH0_PORTAL_ORIGIN` set. Until the portal exists, a run without `first-deployment` fails at `portal-smoke`.
- Deploying the Claude model sends `modelProviderData` (organization, country, industry) and accepts Anthropic's Azure Marketplace terms for the subscription. Foundry Claude refuses credit-only subscriptions; dev uses the pay-as-you-go `fr-com-dev`.
- In Azure, L2 waits in standby for the ledger lock during a revision update (L2-6). Calls get 502 from its sidecar until the old revision releases the lock; L1 reports ERROR and nothing is paid.
- A CDP **Sandbox** key also shows up as `facilitator authentication` (401). Keys are environment-scoped, and the Sandbox has no x402 facilitator. Use a production key; it still settles on Base Sepolia.
